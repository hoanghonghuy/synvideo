# GENERATED_IMAGE_ACQUISITION_V1

Status: FROZEN
Owner: PM / Team Lead
Applies to: TASK-029

## Purpose
Provide a durable, retry-safe creator flow that generates a scene image through the owner-scoped provider runtime, ingests generated bytes into SynVideo MediaAsset storage, and optionally assigns the resulting asset as the scene primary visual without persisting upstream provider URLs or secrets.

## Core invariants
- Use TASK-028 owner-scoped provider/runtime selection and safe internal provider/model IDs only.
- Provider output bytes/streams must become a durable MediaAsset before success is reported.
- Provider output URLs, credentials, ciphertext, base URLs, external model IDs and raw upstream responses must not be persisted in durable jobs/public resources.
- API retries and worker redelivery must not create duplicate logical jobs, duplicate MediaAssets or duplicate scene assignments.
- Scene assignment remains owner/project scoped; cross-owner/project binding is forbidden.
- Failure after durable ingestion must be resumable without regenerating unnecessarily.

## Durable job behavior
The job stores safe internal request identity, owner/project/scene context, internal provider/model selection, lifecycle state, retry metadata and resulting MediaAsset ID when available. Job lifecycle follows the existing durable job framework and propagates cancellation/timeouts to the provider where supported.

## Idempotency / recovery
- A stable idempotency key protects request retries.
- Duplicate worker delivery must be safe.
- The generation → ingestion → assignment boundary needs explicit crash/retry coverage so paid generation is not repeated after a result has already been durably captured.
- MediaAsset creation and scene assignment use existing domain/repository invariants and remain idempotent.

## MediaAsset provenance
Persist only safe provenance required for audit/debugging: generated origin, internal provider/model ID, job/request identity and timestamps. No secrets or external vendor identifiers.

## API / creator behavior
- Creator requests generation for a specific scene using an enabled owner image provider/model.
- API returns durable job identity and truthful status rather than pretending persistence is synchronous.
- Success exposes the durable MediaAsset and assignment outcome.
- Errors remain provider-neutral and distinguish validation, disabled selection, permission/not-found, provider failure and storage failure safely.

## Scope
- durable per-scene image-generation request/job;
- owner-scoped image runtime resolution;
- generated result ingestion into object storage + MediaAsset;
- safe provenance;
- optional scene primary-visual assignment through existing scene media binding;
- retry/idempotency/cancellation/error handling and tests.

## Out of scope
- video generation;
- TTS/narration;
- stock search;
- captions/music;
- editor/composition/render/publish;
- provider-settings or Media Library redesign.

## Acceptance / TDD gate
Acceptance requires evidence for:
1. owner/project/scene isolation and request validation;
2. disabled/unknown image provider/model rejected before generation;
3. durable job creation and idempotent API retry regression;
4. generated bytes ingested into object storage and durable MediaAsset;
5. no provider URL/secret/external ID/raw upstream payload persisted or returned;
6. duplicate delivery/retry does not duplicate logical assets or assignments;
7. crash/retry around generation→ingestion has a tested recovery story;
8. scene assignment is owner/project scoped and idempotent;
9. provider/storage failure and cancellation produce truthful safe states;
10. real PostgreSQL/object-storage integration coverage plus race/full API CI.
