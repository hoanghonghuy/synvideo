## Goal
Introduce SynVideo's first durable product domain: projects that can be created, listed, opened and edited through the web application, persist in PostgreSQL across restarts/refreshes, and are isolated by an explicit owner boundary without prematurely implementing the full authentication product.

This task must establish production-quality persistence/API boundaries that later Creative Brief, scene, asset and channel tasks can build on without redesigning the project identity model.

## Domain contract
A Project has at least:
- `id`: UUID, server generated.
- `owner_id`: UUID, required and never supplied by ordinary project request bodies.
- `title`: required, trimmed, 1..160 characters.
- `description`: optional human-entered project description / early brief seed, max 5000 characters.
- `content_format`: `short`, `long`, or `flexible`.
- `aspect_ratio`: `16:9`, `9:16`, `1:1`, or `4:5` for this task. Keep the domain representation extensible; do not couple it to a social platform.
- `target_duration_seconds`: nullable; when present must be 1..43200.
- `locale`: `vi` or `en`; default `vi`. This is project content locale, separate from application UI locale.
- `status`: `active` or `archived`. Do not encode creative workflow stages in this field.
- `created_at`, `updated_at`: UTC timestamps generated by the system.

Persist constraints that are safe to enforce in PostgreSQL as well as application validation. Do not trust frontend validation as the source of truth.

## Ownership boundary before full authentication
Authentication UI/OAuth/session product is out of scope, but TASK-002 must not create globally unowned projects.

Introduce a small request-principal/actor abstraction in the backend so project services/repositories are owner-scoped from the beginning.

For local `development` and tests only, a configured local actor UUID may supply that principal (for example `SYNVIDEO_LOCAL_ACTOR_ID`). It must not be a source-code constant. Production must not silently fall back to a fake/default actor; if no real principal mechanism exists yet, project routes must fail closed rather than expose cross-user data.

The implementation detail may differ if a cleaner equivalent is found, but these properties are mandatory:
- owner identity is outside project request bodies;
- every list/get/update query is owner-scoped;
- attempting to access another owner's project returns not-found semantics rather than leaking existence;
- the temporary local-development principal is clearly isolated/documented so a later auth task can replace it without changing project domain/repository contracts.

## PostgreSQL persistence
Add versioned migrations and a documented migration command/workflow.

The project table must include appropriate constraints and an index supporting owner-scoped recent-project listing, e.g. owner + updated timestamp + id ordering.

Use a maintained PostgreSQL driver/pool suitable for Go production services. Keep SQL/persistence concerns behind repository boundaries; HTTP handlers must not contain SQL.

Database configuration must be environment-driven and must not commit secrets.

## API contract
Under `/api/v1` provide:
- `POST /projects` — create a project.
- `GET /projects` — owner-scoped list, newest activity first.
- `GET /projects/{id}` — owner-scoped detail.
- `PATCH /projects/{id}` — partial update of editable project metadata/status.

List endpoint must support bounded pagination (`limit`, default 20, max 100) and a stable continuation mechanism. Prefer an opaque cursor over page-number pagination so ordering by `updated_at` + `id` remains deterministic as data changes.

Use one consistent JSON error envelope for validation/not-found/internal errors. Validation responses must be actionable without exposing SQL/internal implementation details.

Do not expose `owner_id` as a writable client field.

## Backend structure
Maintain clear separation between:
- HTTP transport/parsing/error mapping;
- application/service logic;
- project domain validation;
- persistence repository;
- request principal/actor resolution.

All DB and HTTP work must honor request context/cancellation. Avoid global mutable database state.

## Frontend scope
Implement only the product UI needed to prove this foundation:
- project list route/view;
- clear empty state;
- create-project flow with the domain fields above;
- open project detail route;
- edit and persist project metadata;
- loading, submitting, validation and recoverable API error states;
- refresh/reopen must show persisted data from the backend, not local mock state.

All user-facing strings must use the existing i18n mechanism. Vietnamese is the active UI locale; do not scatter hard-coded strings in components.

Do not turn this task into the final dashboard/editor visual design. Functional UX and clean component boundaries matter more than visual polish here.

## Acceptance criteria
TASK-002 is acceptable only when all are true:
1. A user in local development can create a project in the web UI, refresh the browser/server, and see/open the same persisted project.
2. Project create/get/list/update are persisted in PostgreSQL and are not backed by in-memory or browser-only storage.
3. Project records are always scoped by the resolved owner/principal; tests prove one owner cannot read/update another owner's project.
4. Invalid metadata is rejected consistently at the API boundary and safe constraints also exist in the DB where appropriate.
5. List ordering/pagination is deterministic and bounded.
6. Loading/empty/error/submitting states exist in the web flow and all visible copy goes through i18n.
7. Migrations are versioned, repeatable on a clean local database, and exercised by CI/integration tests.
8. No secrets, fake production identity fallback, AI generation, scene/media behavior, or platform-specific publishing logic is introduced.
9. Existing TASK-001 health/readiness behavior and verification continue to work.
10. Behavior implemented after TDD adoption follows `docs/engineering/TDD_PROTOCOL.md`, and already-written behavior has sufficient regression coverage before acceptance.

## Out of scope
- Login/signup/OAuth/session UI and full authentication product.
- Teams/workspace collaboration and invitations.
- AI proposal/script generation.
- Creative Brief workflow beyond storing the early free-text `description` seed.
- Scene editor, assets, uploads, generation, rendering.
- Billing/credits/provider keys.
- Channel connections/publishing/analytics.
- Hard delete/purge lifecycle unless separately specified.
